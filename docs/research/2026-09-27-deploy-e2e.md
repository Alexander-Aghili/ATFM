# Deploy path end to end on the laptop (2026-09-27)

> **Dated research record.** Findings and plans below retain their original scope.
> See [current implementation status](../status.md) and [current run instructions](../operations.md).

`scripts/l1_control_e2e.sh`: Dynamo Mocker workers and frontend, the proxy asking the board service for
per-request predictions (`--board`), 20 scripted sessions with 57 real tool phases through the sidecar,
the board service with controllers attached from `experiments/control_local.yaml` and a metrics scrape,
and the control loop pushing directives to the proxy every 2 s for 30 steps. A functional check, not an
experiment.

Outcome (exit 0, no errors in 30 control steps):

- Events flowed harness -> sidecar/proxy -> JSONL bus -> board: the board saw up to 6 concurrent sessions and
  produced snapshots (background q50 KV demand 94 / 221 / 433 / 778 / 1741 blocks at 10 s / 30 s / 2 min / 5 min / 15 min).
- The replica floor proposed 1 replica (q90 demand 1,557 blocks at the 300 s lead time against 8,000 per replica).
- The tier logger issued demote directives for sessions inside long pytest phases.
- The proxy served every call with the board in the loop (queue empty at the end, no caps, no alarms).
- **Holds and touches were 0**, because the metrics scrape found no KV metrics on the Mocker frontend's `/metrics`
  (capacity stayed empty, so the GDP planner did not run, and no eviction frontier was set, so the touch
  controller had no candidates). The controllers are wired; the capacity input needs a worker metrics page,
  which the real vLLM workers expose and Mocker does not.

What this establishes: the deploy topology of the spec (figure 2) runs as one system on a laptop. What it
does not establish: any effect of the controllers, which needs real worker metrics and, for placement, the
H100 study.
