\subsection{Control implementation and scaling}
\label{sec:control-implementation}
The live prototype and the policy simulations have distinct performance costs.
The implementation revisions described here address live control overhead; they
do not revise the reported simulation outcomes or establish hardware throughput.

\paragraph{Incremental event consumption.}
Previously, live JSONL draining reused the full-file offline reader, so each tick
parsed and reapplied historical records. A per-consumer byte cursor now separates
incremental consumption from full replay. With bounded event size, parsing costs
$O(\Delta E)$ for newly appended events rather than $O(E)$ for the entire history;
an unchanged log needs only a metadata check. A new board still replays from the
beginning to reconstruct state. Complete malformed lines are counted and skipped,
partial last lines are retried, and observed truncation or file replacement resets
the cursor. Rotation requires coordination to avoid losing an unread old-file tail;
unobserved copy-truncate/regrowth is unsupported. This cursor does not checkpoint
model state or acknowledge successful downstream application. Crash-safe recovery
still requires consistent state/log checkpoints and duplicate handling. Consumed
arrival records are discarded while future timestamps are retained, preserving
the existing exclusion of starts older than the previous board tick.

The design prioritizes event semantics before CPU kernels. Tests exercise repeated
drains and board ticks, partial and malformed lines, independent readers, file
replacement, observed truncation, and I/O retry. Component benchmarks and their
source hashes accompany the development documentation; none measures GPU service
capacity or end-to-end tail latency.

\paragraph{Batched control delivery.}
Previously each hold caused a serial HTTP request and a fresh queue scan. The
controller now sends bounded batches of at most 1,024 holds. The proxy validates
all records before applying a batch, discards expired updates, and performs one
admission pass. For $D$ directives, backlog $Q$, and batch bound $B$, the repeated
list-scan term changes from $O(DQ)$ to $O(D+\lceil D/B\rceil Q)$, excluding release
selection. Round trips decrease from $D$ to $\lceil D/B\rceil$; payload work stays
$O(D)$. Chunks are independent, not a durable whole-plan transaction. Updates
retain their original meaning: they govern subsequent submissions and do not
retime already queued requests. Versioned deltas and automatic retry are deferred
because expiry renewal and restart synchronization require a separate protocol.
The per-request board client also retrieves service and next-tool estimates in
one request, with local fallback on unavailable results. CPU work still shares
the board event loop; these changes do not establish request-tail isolation.

\paragraph{Indexed admission.}
The live queue previously scanned its pending list for every individual completion.
It now maintains priority and FCFS ready heaps, delayed-release and promotion
heaps, and request-identity dictionaries. Stable insertion sequences resolve ties;
versioned records invalidate old priorities, and periodic linear-time rebuilds
bound stale heap storage. Ordinary release costs $O(\log Q)$ amortized, reducing
individual backlog drainage from $O(Q^2)$ to $O(Q\log Q)$; simultaneous due events
still require processing each affected request. Overflow transitions retain the
original hold-dropping and FCFS policy and can cost $O(Q)$. A single wake-up timer
tracks holds and promotions. Randomized differential tests compare release order
and state with the former scan implementation. Diagnostic counts and peer-rank
queries still scan the backlog, so this is not a logarithmic bound on the whole
HTTP request path. The simulator's worker queue is a separate implementation.

\paragraph{Planner search and forecast sampling.}
GDP search now bounds candidate slots before allocation using the original delay
comparison. For $S$ sessions, $F$ total slots, and $W$ eligible slots, vector search
costs $O(SW)$ plus $O(S\log F)$ interval-bound work, excluding threshold preparation
and sorting. For larger windows, a lazily constructed segment tree stores
per-resource minima of the exact threshold-plus-commitment quantity. A range is
skipped when any resource cannot fit even at that minimum. Passing a range test
does not imply joint feasibility, since resource minima can occur in different
slots; leaves retain exact comparisons. Search therefore remains $O(F)$ in the
worst case, with $O(\log F)$ commitment updates for fixed resource count. Small
windows retain vector search, and open cases need not build the tree. Tests compare
full directives and assignments with the original sample-scan planner, including
floating-point boundaries and tenant-cap overrides.

Empirical forecast sampling uses integer-indexed draws instead of generic
unweighted replacement choice. This preserves sampled values and random-stream
consumption under the tested NumPy generators while reducing repeated small-call
overhead. It does not change the $O(SMH)$ aggregation order for $M$ draws and $H$
horizons, nor introduce shared session samples. Cross-session batching, reuse of
forecast draws for directive quantiles, and separation of control computation
from request handling remain future work requiring statistical or state-ownership
validation. The implementation changes do not imply a change in forecast quality.

The JSONL fixture has no newly appended events; its initial replay still reads

\paragraph{Integrated load-test harness.}
A separate experiment package now runs the real proxy, board, and control loop
against a bounded-concurrency fake model worker in independent localhost HTTP
processes. Scheduled new-session arrivals remain independent of earlier sessions;
each session makes sequential model calls separated by tool progress and completion
events. A synchronized-completion variant exercises bursts. The harness retains
client and proxy traces, control-call timings, observed queue depths, snapshot age,
process CPU/memory, event-loop lag, generator lateness, and incomplete-run outcomes.
Its initial six cases completed 2,016 synthetic calls without request or control
errors. Trace alignment exposed substantial pre-proxy delay in one burst case,
so client transport timestamps were added before attributing that delay to the
scheduler. An instrumented reuse trial retained one client transport error and
confirmed delays before sending headers. A fresh-connection trial completed all
768 calls with much shorter pre-proxy delay. Connection reuse is therefore an
explicit harness setting; these single-run comparisons do not establish a
production-client tuning rule. These are finite single-run integration checks, not hardware capacity
or policy-quality results: the fake worker has fixed service delay and no model
kernels, cache behavior, transfer cost, or token streaming. Exact configurations,
source hashes, compressed raw evidence, and limitations are recorded in the
repository's HTTP load-baseline report.

\paragraph{Repeated control attribution.}
A follow-up uses three paired seeds with periodic control enabled or disabled,
alternating run order at 256 and 1,024 sessions. Proxy counters distinguish
returned predictions from caller timeout fallback, other errors, and cancellation.
Control-off also removes refreshed board state and policy actuation, so this is
an operational ablation rather than an equal-information policy comparison.
An inherited 1,024-file-descriptor limit caused socket-accept exhaustion in some
large cases; those failed trials are retained separately. Repeating the large
cases with a process-local limit of 8,192 completed all 18,432 calls.

With eight fake-worker slots and 50\,ms service, measured throughput was
147--151 calls/s, close to the ideal service bound of 160 calls/s.
Client p95 across the three runs was 8.17--8.28\,s with control and
8.27--8.69\,s without. Despite similar saturated throughput, pooled prediction
timeouts were 37.47\% with control versus 10.88\% without; maximum sampled board
event-loop lag was 197--214\,ms versus approximately 2\,ms.
Control computation, populated state, policy actions, and changed request timing
remain combined in this contrast.

A separate series gives the fake worker 64 slots and 5\,ms service and sets the
proxy window to 64. All 18,432 calls succeed, but finite-workload throughput is
only 307--345 calls/s. No worker waiters are observed; proxy process CPU is
9.08--10.17\,s during approximately 8.9--10.0\,s of workload, consistent with
roughly one busy core, with slightly different accounting windows.
Caller prediction timeouts remain 46.41\% without control and 56.98\% with it.
Client p95 ranges overlap, and the sign of the paired latency difference varies.
Generator lateness and transport costs are also material. These measurements
motivate profiling the proxy request path and isolating deadline-sensitive
prediction handling from control work; they do not identify a particular hot
function, establish sustained serving capacity, or justify a language rewrite.
The repository's repeated-control-attribution report retains configurations,
source hashes, compressed raw evidence, and individual results for all 24 trials.

\paragraph{Proxy profiling and a transport dependency correction.}
Per-thread CPU profiling of the fast-worker workload identified repeated
missing-module searches in HTTPcore's asynchronous-runtime detector.
The tested serving environment lacked its optional \texttt{sniffio} dependency.
Two instrumented runs spent 4.10--4.44\,s in runtime detection on the serving
thread, versus 1.32--1.33\,s scanning queued peer indices and 0.58--0.61\,s
publishing events. These are profiler-inflated cumulative function timings,
not uninstrumented request costs. Supplying \texttt{sniffio} reduced the detector
to 0.067--0.068\,s in follow-up profiles. A focused unprofiled test reduced
10,000 checks from a seven-repeat median of 255.11\,ms to 2.45\,ms.

Three paired seeds per control mode then compared otherwise identical package
environments with and without the dependency, alternating trial order.
All 36,864 calls succeeded. With periodic control, the median of run p95
latencies fell from 3.495 to 2.437\,s and median proxy CPU from 9.046 to
6.892\,s; without control, these changed from 4.035 to 3.007\,s and
9.772 to 7.825\,s. However, pooled prediction timeout rates increased from
55.62\% to 63.31\% with control and from 38.43\% to 47.81\% without.
The dependency is available to the generator and all services, so the integrated
effect includes changed request timing and prediction completion patterns.
These results support removing redundant import work but do not demonstrate
better scheduling quality or establish a universal speedup.
The serving extra now supplies the detector explicitly; scheduling algorithms
are unchanged. Those trials motivated the subsequent bounded prediction path described below.
Thread-aware profiling remains an optional experiment dependency, and the
repository's proxy-profiling report preserves all individual trials and
measurement limitations.

\paragraph{Behavior-preserving maintenance.}
A subsequent core refactor consolidates sidecar execution and configuration,
simulator callbacks and index calculations, and trace/forecast schema helpers.
Ten deterministic simulation policy variants preserve request, session, and
random-generator-state hashes; an 8,192-session forecast preserves its result
hash. A shared per-line parser helper was rejected after a 4.9\% microbenchmark
regression, retaining inline parsing. The retained sidecar paths preserve output
and event hashes; their 21-sample medians differ by +1.8\% for wrapped output and
-0.1\% for subprocess output. These short synthetic measurements support the
maintenance decision, not universal performance equivalence. The final suite
passes 420 tests with five skips. The dated core-refactor report records the
fixtures, intermediate revisions, raw timings, and validation limits.


\paragraph{Implementation structure and equivalent execution.}
The September 28 modularity pass separates application handlers, predictor
fitting, event processing, simulation transitions, and experiment reporting into
functions of at most 20 source lines. Explicit depth-first stacks replace recursive
synthetic-family generation and cloning while preserving seeded draw order.
The GDP implementation caches its exact hold-window boundary search by starting
slot within each planning pass; feasibility itself remains uncached because
committed demand changes. For $N$ sessions, $S$ slots, and $U\leq S$ distinct
starting slots, boundary-search work is $O(U\log S+N)$ with $O(U)$ storage.
This is an implementation change, not an additional forecast or policy claim.
The reproducibility record in \texttt{docs/research/results/modularity-2026-09-28/}
reports output equivalence and CPU timing limits.


\paragraph{Bounded prediction admission (September 28).}
The proxy now admits at most $L$ unfinished prediction jobs ($L=4$ by default),
with immediate local fallback when full. Its monotonic caller deadline includes
executor dispatch and prediction; an expired job skips computation. A timeout or
caller cancellation does not release capacity held by a running thread: only
future completion does. Board HTTP phase timeouts use the remaining caller
budget rather than a 500\,ms minimum. The caller also rejects results after its
deadline. Event-loop stalls can delay timeout handling, and remote computation
may outlive the HTTP request; neither hard real-time behavior nor server-side
cancellation is claimed.

Admission and accounting require $O(1)$ work per request and $O(L)$ unfinished
jobs. Counters distinguish immediate rejection, caller timeout, prediction use,
and outstanding/running/completed worker jobs. Shutdown drains the executor
before closing owned clients. This preserves fallback estimates and scheduling
formulas but can change which predictions are used and therefore request order.
Board computation still runs synchronously in its service handlers; isolating
that mutable state remains separate work. Paired CPU-only HTTP trials and their
source hashes are retained in the September 28 prediction-overload study.

In three paired fast-worker trials at each size, client p95 decreased in all six
pairs: the three-run ranges changed from 0.503--0.825 to 0.427--0.557\,s at 256
sessions and from 2.311--3.465 to 1.851--2.926\,s at 1,024 sessions. However,
pooled timely prediction use fell from 58.42\% to 52.00\% and from 32.26\% to
18.98\%, respectively; immediate rejection accounted for 36.98\% and 71.69\%
of candidate attempts. All 23,040 planned calls completed, and candidate peak
unfinished prediction work was four. This is a bounded-work result with a
latency/coverage trade-off, not evidence of improved policy quality. Ranges are
not confidence intervals. Baseline shutdown logs contain a pre-existing cleanup
failure after measurement; the candidate lifecycle removes it. The study retains
both versions' logs, configuration and source hashes.
