# Stage E: forecast-driven LMCache warming on H100s: 30 September 2026

Design: [stage E spec](../superpowers/specs/2026-09-30-stage-e-design.md); runbook:
[stage E arms](../development/gpu-public-workloads.md#stage-e-arms-forecast-driven-warming);
software at `45bbf93`. Evidence: [results/gpu-stage-e-2026-09-30](results/gpu-stage-e-2026-09-30/).

**Outcome:** the complete ATFM warming path ran on real GPUs without errors, but the
experiment is **inconclusive** about benefit or cost. Within each Pod, replay
performance drifted with run order by more than any plausible arm effect, and the
replayed agent left a median 1.6 s between calls, far less than the ~8 s needed to
warm its ~80k-token contexts. Compute cost about 13.8 USD.

## Setup

The 119-request multi-branch Weka root at a 24 GiB CPU tier and 16-token chunks
(round 3's capacity-pressure setting), Qwen3-4B, vLLM 0.30.0, LMCache 0.5.5. Arms:
`direct` (AIPerf -> vLLM), `proxy` (AIPerf -> ATFM proxy -> vLLM), `atfm-q10` and
`atfm-q50` (proxy + board + control loop issuing asynchronous L2 -> CPU warms; q10
warms when an early return is plausible, q50 when the median return is within lead
time + one interval and re-warms after 30 s). The board's survival model was trained
on the AgentX table with the three replayed roots removed (98,663 rows,
sha256 `e465dcc8...`). Each Pod ran all four arms once in a seeded order
(`random.Random(20261001)`).

The first two Pods landed on the same physical host (same address, different GPUs).
Because warming is host-bound, Pod A was terminated after its first arm began and
replaced by Pod C in another data center. Pod B's first arm (`proxy`) overlapped Pod A
and is excluded.

Every replay completed 119/119 requests and 4/4 child branches. Pod B (US-NE-1)
improved run by run and Pod C (US-MO-1) degraded from its first run to its third, so
`atfm-q50` was best on B (-26% duration, -67% median TTFT against direct) and worst on
C (+43%). Round 3's bracketed order had shown 1-3% spread within a setting; one shuffled
order per Pod cannot separate arms from drift. Pod C's host showed a load average of
16-20 from other tenants during the runs, a plausible but unproven cause.

## Why warming could not help here

Across every proxied replay the gap between a call's end and the same session's next
request was 0.84 / 1.64 / 1.96 s (p10 / p50 / p90); only 2 of 114 gaps exceeded 5 s,
one being the parent's 14-23-minute wait for its sub-agents (`gap-analysis.json`).
Contexts were ~80k tokens (max 106k), which stage C showed take ~8 s to warm. Warms
were issued a median 0.6-0.9 s after a call ended and landed 0.6-0.9 s before the next
request, so they could not complete in time. 82 of 108 settled warms were partial
(fewer keys found than requested), most likely because chunks that failed L1
allocation were never stored; the actuator logs outcome counts, not keys per warm.
On Pod C both warming arms had lower hit ratios and more allocation warnings than
`direct`, consistent with warm traffic competing for the CPU tier.

## What it establishes and what would decide it

Established: the proxy -> board (held-out forecasts, gap phase, PrefetchPlanner) ->
control loop -> LMCache MP path works on real GPUs under a real agent replay, and the
deciding quantity is the idle window before a return relative to the measured warm
time. Not established: any latency or duration effect of forecast-driven warming, or
the proxy hop's own cost.

Next: bracketed orders (A-B-B-A, at least three runs per arm per Pod) with host-load
telemetry; workloads with multi-second tool phases; per-warm found/expected keys;
an isolated proxy-hop measurement; and runs at 48 GiB with 64-token chunks, the better
baseline, as well as at 24 GiB.
