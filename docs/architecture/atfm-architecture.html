ATFM Architecture

Air-traffic-style flow management for agent fleets on a shared NVIDIA Dynamo GPU pool: forecast demand from in-flight sessions, order calls by class, delay deferrable work on the ground.

Design v1.1 · revised 2026-09-23 after external review · status updated 2026-09-23 · source: docs/superpowers/specs/2026-09-22-atfm-architecture-design.md

Where this stands (2026-09-24)

Three implementation passes exist on top of this design, all test-driven and reviewed (141 tests). The numbers below are the only results so far and are reported with their metric, horizon and split so they cannot be over-read.

L0 · done · 45 tests

Forecast core

Canonical trace schema, TraceLab adapter (357k rounds, 4,265 sessions), Poisson overlay and time-block split, fleet replayer, predictor ladder B0 to M3, Monte Carlo forecaster, CRPS / pinball / coverage / surge metrics, synthetic fleet generator, H1 runner.

L1 · built and reviewed · 91 tests plus 2 gated

Plumbing on the laptop

Event schema and buses, byte-exact sidecar with pytest / percent / counter / rate parsers and a launch gate, mini-SWE-agent adapters (local and Docker), the proxy with global window and priority tiers, live demand board, Dynamo Mocker launcher, scripted trace collection, coverage report, H1b runner.

Verified on this machine

Dynamo v1.5 stack

Mocker workers plus the frontend start with file discovery in about four seconds and serve a request carrying nvext.agent_hints. An end-to-end run with three concurrent scripted sessions through the proxy held the window at two and gave the deadline-bound interactive session the top tier.

H1b · gate passed (long-tool regime)

Long-tool trace collection

16 real phases of 78 to 345 s (cmake builds at two parallelism levels, linear and staged pipelines at four sizes), plus two runs of the numpy test suite (49,696 tests, 200 s, 51k progress events each), scored per session every 15 s with the job family held out: the progress signal cuts remaining-time error 2.8x over elapsed time alone (q90 pinball 8.9 vs 24.9 on 202 points; CRPS 30.1 vs 59.0). numpy is S-shaped in progress and M2 only beats M1 once one prior run of the suite is in training (CRPS 18.8 vs 53.7). Earlier figures without numpy: q90 pinball 10.0 vs 28.1; CRPS 17.8 vs 59.7), 10 to 30x on linear output, 2 to 5x on staged output, and 1.2 to 15x on cmake percent markers once a per-tool progress curve is learned from another build. Eight job families on one machine; the numpy suite is being added.

L0 policies · built, reviewed, fixed · 3 regimes run

Closed-loop simulator, six arms

Heap event loop with KV LRU workers, prefix reuse and priority batching; proxy window, tiers, capped and re-consulted holds; arms native, proxy rules, forecast M1, forecast M2, oracle, ThunderAgent-style working set, plus a no-hold ablation. Every arm logs where each call waited and what a hold cost (hold seconds, held KV block-seconds, evictions attributed to holds, recomputed prefill). Synthetic programs only; see the H2 table below. Note: docs/research/2026-09-24-h2sim-first-results.md.

H1a evidence: in-flight session state versus history baselines, two corpora

Ratio of the Kalman baseline's q90 pinball loss to the elapsed-time model's (above 1 favours in-flight state), mean over 3 seeds at 100 / 200 / 400 sessions per hour. TraceLab (4,265 real Claude Code and Codex sessions, held-out calendar weeks): 1.0 to 1.1x at 10 s rising to 3.0 / 4.0 / 5.1x at 15 min. AgentX (393 Claude Code sessions with real sub-agent fan-out, held-out families): 1.1 to 1.5x at 10 s rising to 3.0 / 4.3 / 5.4x at 5 min, about 3x at 15 min with wide seed variance. The per-tool history predictor that ignores elapsed time is the worst model on both corpora. Full tables: docs/research/2026-09-23-h1-second-corpus-and-h1b.md.

Elapsed-time conditioning beats the Kalman baseline by 1.9x at 2 min, 2.1x at 5 min and 3.4x at 15 min, and loses by 18% at 10 s. Demand is 81 to 99% endogenous at these horizons. The session models are under-dispersed (40 to 71% coverage of a 90% interval); out-of-sample dispersion calibration lifts that to 65 to 86% but not to 90, which says the remaining miss is bias on sessions and tools unseen in training rather than variance. On a synthetic fleet with progress-emitting tools, live progress (M2) adds 30 to 40% over M1 at 10 s to 5 min on background work; on TraceLab M2 equals M1 because no progress events exist, which is exactly why the L1 collection is needed.

Two harness bugs found in review were fixed before these numbers: a shared exogenous-arrival model multiplied the arrival rate by the model count, and the pending state after a tool was treated as due now although the tool-end to next-request gap has a heavy tail in TraceLab (p99 45 s, max 128 h). System context: what talks to what

Two paths leave every agent harness. The request path carries LLM calls through our proxy into Dynamo. The state path carries tool progress from the sidecar over the event bus to the demand board, which feeds the controllers. Nothing on the state path can block the request path.

atfm.proxy

Harness proxy

OpenAI-compatible ASGI server. Classifies the session, asks the board for predictions, computes the index, holds or releases, writes hints and headers, forwards the body untouched, logs every call.

atfm.sidecar

Tool-runtime sidecar

Wraps tool subprocesses in the harness. Streams output through parsers (pytest, builds, dbt, training logs) that emit progress and data events. Output reaches the agent byte-for-byte.

atfm.board

Demand board

Session registry plus the predictor ladder B0 to M3. Every 5 s draws 512 Monte Carlo futures of the fleet and publishes KV and prefill demand per horizon and class.

atfm.control

Controllers

Ground delay program (30 s slots, chance constraint on samples, ration-by-schedule order), pre-staging across tiers, replica floor via the Dynamo planner plugin.

atfm.dynamo

Dynamo adapters

Hint encoding, SGLang HiCache pinning, worker metric scraping, Mocker launcher, planner gRPC stub. The only package that knows Dynamo's wire formats.

atfm.sim · atfm.eval

Simulator and evaluation

Discrete-event fleet model using the same policy and controller classes as deployment. Forecast scoring (CRPS, pinball, coverage, lead time) and serving metrics with paired bootstrap CIs.

What a session turn moves through

A session alternates between running a tool and waiting for an LLM call. The demand board predicts the time until each session leaves TOOL_RUNNING. The proxy's index acts at LLM_PENDING. Only the engine can preempt LLM_RUNNING.

Where the queue lives, and why a window is needed

Ordering only sticks at the layer that holds the backlog. If the proxy forwards everything immediately, the backlog forms inside the engine and the engine's policy decides. The proxy therefore keeps at most a fixed global window of requests in flight across the pool and orders the rest itself. A per-worker window is not enforceable here: Dynamo picks the worker after the proxy releases the request, and owning selection means owning reservations, forwarding, streaming and cleanup too. The class tier is written into the priority hint so that any backlog that still forms below keeps class order.

The index, its objective, and what goes into the hint

objective   minimize Σ w(class_i)·C_i + λ_int·(interactive SLO misses on TTFT after tool return)
                     + λ_bg·(background deadline misses)     s.t. per-class delay budgets

π_i = w(class_i) · (1 + β · E[T_tool_next,i]) / E[S_i]

w / E[S]          c-mu rule: optimal for weighted completion time on one server with known sizes
E[T_tool_next,i]  unblocking term: a critical-path heuristic, always ablated with β = 0
slack override    if deadline_i − now − E[S_i] < threshold → top tier
hint              strict_priority ∈ {2 slack, 1 interactive, 0 background}; priority = coarse bucket of π
                  tiers are class and deadline facts, so a released request's hint never goes stale;
                  fine ordering is recomputed inside the proxy on every arrival

Demand board: from per-session posteriors to a fleet forecast

Each session in TOOL_RUNNING gets a distribution over when it will next need the GPU and how much. Draws from all sessions are summed, children are spawned recursively, and exogenous arrivals are added. The output is a set of samples per horizon, never a point estimate.

What M2 does with a progress stream

For a tool reporting completed work w of total W, the board keeps a Gamma posterior over the work rate updated by each (Δw, Δt) increment, and a small phase model for tools whose end phase reports nothing (teardown, upload). Remaining time is (W − w)/r drawn from the posterior plus the end-phase residual. Data events (loss curves, failing test counts) update an early-stop probability that truncates the distribution. When no progress events arrive, M2 is exactly M1.

Ground delay: holding background work, at a stated cost

Holding a deferrable call in the proxy trades background completion time for interactive latency. It is a cost, charged against a per-class delay budget, not a free action. The proxy can only act on a request that has arrived: while a tool runs, the program plans provisionally, and the decision is made at arrival. Delaying earlier than that needs the separate launch gate in the sidecar. Every 30 s the program looks 15 minutes ahead in 30-second slots, with interactive demand per slot as a random variable from the forecast samples for both KV blocks and prefill tokens per second, and assigns deferrable sessions provisional release slots so the overflow chance stays below ε per slot and per resource, in ration-by-schedule order.

Memory tiers: future work, and what v1 measures instead

The same per-session distribution would decide where a paused session's KV should live: keep and pin when likely to resume soon, demote when not, promote or speculatively prefill when the lower quantile of the remaining time falls inside the tier's lead time. No shipped API implements that placement for one session today, so this is deferred until a mechanism is demonstrated end to end. What v1 measures on the real backend is the cost of holding: a held session's prefix stays in the engine's cache subject to its eviction policy, so the cost is cache occupancy while held, evictions of other prefixes it causes, recomputed prefill when it resumes, and the background delay itself.

Sidecar: two paths out of every tool call

The sidecar wraps the harness's tool subprocess. The result path is a byte-for-byte pipe back to the agent. The state path tails the same output through a parser chain and emits progress and data events. If the bus is down, events are dropped and counted; the agent never notices.

Simulator and evaluation share the deployment code

Built (src/atfm/sim): programs (synthetic or from a trace table, with overlay cloning and context-reset turns), a worker engine with KV LRU, prefix reuse, capacity-based free blocks and head-of-line priority batching, a heap event loop with proxy queue, window and holds that are capped in the core and re-consulted at expiry, per-call lifecycle rows, six policies plus a no-hold ablation, serving metrics on makespan, and a paired multi-seed runner. Still per the design and not yet built: memory tiers, prefix-affinity routing, perturbation schedules, replay of real trace tables through the arms.

The simulator is a heap-based discrete-event loop with no framework dependency. It instantiates the same policy, predictor and controller classes as deployment and drives them on simulated time. Its outputs are the same trace table and metrics as a real run, so a paired sim-versus-real comparison is a diff of two identical files.
