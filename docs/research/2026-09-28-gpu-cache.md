# Real GPU LMCache integration: 28 September 2026

**Result:** ATFM's pinned LMCache MP actuator completed disk-to-CPU warm
prefetch, and subsequent real vLLM inference reused the cached prompt. This is
hardware compatibility evidence, not a policy-performance result.

- Linux x86-64, Python 3.12.13; vLLM 0.30.0, LMCache 0.5.5, PyTorch 2.13.0
  with CUDA 13.0. Full installed versions accompany each run.

  `c1899de289a04d12100db370d81485cdf75e47ca`.
- One engine, tensor-parallel world size one; 2,048-token context, at most two
  sequences, eager execution, GPU memory utilization setting 0.55.
- LMCache MP: 16-token chunks, 0.5 GiB CPU L1, filesystem L2, LRU eviction.
- vLLM's own prefix caching disabled. Services bound to loopback. No paid
  resources or external messages were created.

## Procedure and results

Each run starts fresh owned services and a new disk cache directory. The same
synthetic 352-token prompt requests eight output tokens at temperature zero and
seed seven. After cold fill and idle storage, the runner clears only its own L1,
checks that it is empty, then issues an ATFM CPU-prefetch directive. It requires
completed retrieval of every expected key, verifies occupancy and lock state,
and submits the second inference request.

LMCache's logs additionally report retrieval of the aligned 352-token prefix.
The final repeat reconstructs a separate environment from all 224 pinned
packages using the local wheel cache; `uv pip check` found no incompatibilities.
It then starts new services and repeats the same real inference check.

Earlier exploratory successes are not included in this table.

## API correction

The earlier adapter assumed legacy pin/move/lookup/unpin endpoints. The selected
MP release exposes a warm-prefetch job API instead. The replacement validates
backend version, chunk size, acknowledgement and completion; it retains an
immutable token snapshot while a job is pending and limits pending job count.
It rejects partial/unknown outcomes as unsuccessful and reports unsupported
pinning or GPU placement explicitly. There are no pin leases to release.

These choices matter: HTTP acceptance does not prove transfer completion; CPU
warming does not prove GPU residency; prefix retrieval does not prove a useful
scheduler. The manual CPU directive validates the actuator, not the board's
choice of action. GPU-targeted board proposals remain unsupported by this API.

## Limits and next measurement

This small deterministic prompt is not a representative agent workload. There
are no tool calls, inter-call delays, concurrent-session pressure, evictions,
network transfers, multi-node workers, or statistical policy comparisons here.
OS page caching may accelerate filesystem reads. Full-suite CPU tests ran
during some checks; the observed HTTP durations must not be used as a claimed
ATFM speedup or hardware-capacity estimate.

The next hardware gate is to repeat the unchanged compatibility check on one
H100. Only after that should a representative, context-compatible public trace
subset compare ordinary LMCache, observation-only ATFM and one supported action
at identical budgets. Keep the [AIPerf CPU smoke](2026-09-28-local-cluster.md)
separate: it changes delays/output sizes and cannot supply faithful policy data.
